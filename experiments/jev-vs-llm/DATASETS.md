# Public benchmark datasets

The public benchmark tier deliberately uses externally labelled datasets rather than labels generated by Jev or the LLMs under test.

## BANKING77

**Purpose in this repo:** 77-class intent routing (closed-set classification) and the in-scope half of the calibration benchmark (open-set detection).

Canonical source:

- PolyAI-LDN/task-specific-datasets
- Reference: *Casanueva et al. (2020), "Efficient Intent Detection with Dual Sentence Encoders Applications to Real-World Mobile Banking Queries"* (PolyAI)
- License: CC BY 4.0
- Canonical split files: `banking_data/test.csv`, `banking_data/categories.json`
- Full dataset size: 10,003 training examples, 3,080 test examples across 77 intents.

### What "Routing" Means in this Benchmark

In this benchmark, **routing does not refer to network packet routing or technical infrastructure routing**. Instead, it represents **customer intent routing / intent classification** in an enterprise banking support scenario:

```text
Customer Support Message
            ↓
Classifier / Decision Engine
            ↓
1 of 77 Predefined Intent Destinations
```

Concrete examples from the dataset:

```text
"I haven't received my new card yet"
        ↓
card_arrival

"I was charged twice for the same transaction"
        ↓
card_payment_fee_charged / wrong_amount_of_cash_received

"I forgot my PIN number"
        ↓
pin_blocked / change_pin
```

### Why BANKING77 is Especially Relevant for JEV vs LLMs

BANKING77 is not a simplistic 3-way toy classification (e.g. `billing`, `technical_support`, `other`). It presents a rigorous real-world test because:

1. **77 fine-grained classes with high semantic adjacency**: Multiple intents address closely related operations (e.g., distinguishing `card_arrival`, `card_delivery_estimate`, `card_not_working`, `card_linking`, `lost_or_stolen_card`). The model cannot rely on trivial keyword matching.
2. **Realistic bounded decision space**: In customer service automation, a system must route queries into a fixed catalogue of enterprise actions, workflows, or departments.
3. **Structured decision engine vs token generation**: JEV exposes a native probability distribution across the candidate choices (`Choice`), whereas an LLM must parse the candidate list in context and output structured JSON, testing reasoning efficiency, latency, and JSON grammar compliance.
4. **Latency and cost sensitivity**: In production customer support, routing decisions must be fast (<100ms ideally) and cheap. Running a massive general-purpose LLM on high-volume ticket routing is economically inefficient; small local models or dedicated engines like JEV are prime candidates.

### Evaluation Workflow

The benchmark sends raw customer query strings directly into both systems and compares predictions against the upstream ground truth:

```text
                    BANKING77
                         │
                         ▼
           "Customer message string"
                         │
          ┌──────────────┴──────────────┐
          │                             │
         JEV                           LLM
          │                             │
          ▼                             ▼
   predicted_intent              predicted_intent
          │                             │
          └──────────────┬──────────────┘
                         ▼
             Official Ground Truth
```

The benchmark measures:
- **Accuracy** with 95% Wilson score confidence intervals;
- **Macro-F1** across all 77 classes (to ensure equal weight across all intents);
- **Structured JSON validity rate** (for LLMs);
- **Client-observed latency** (p50, p95, p99);
- **Cost per decision** (token pricing or local runtime footprint);
- **Top confusion pairs** (analyzing semantically adjacent errors).

### Ground Truth Fidelity and Splits

- The benchmark uses **strictly the official test split of BANKING77** (3,080 human-annotated examples).
- **Zero synthetic ground truth**: No labels are generated by GPT or JEV. Upstream human annotations serve as the single source of truth.
- On disk, data is downloaded on demand into:

```text
data/cache/banking77/
```

No raw dataset rows are committed to this repository.

## CLINC150 / OOS evaluation dataset

**Purpose in this repo:** out-of-scope examples for calibration and rejection behavior.

Canonical source:

- clinc/oos-eval
- Reference: *Larson et al. (2019), "An Evaluation Dataset for Intent Classification and Out-of-Scope Prediction"* (EMNLP 2019)
- License: Creative Commons Attribution 3.0 Unported
- Canonical split: `data/data_full.json`, split `oos_test` (1,000 out-of-scope test examples)

The benchmark first applies a conservative lexical filter that removes OOS examples containing obvious finance/banking vocabulary, reducing accidental overlap with BANKING77. The remaining `oos_test` examples are mapped to the explicit BANKING77 `other` option. This turns the calibration task into:

```text
77 supported banking intents
+ other / out-of-scope
```

The data is downloaded on demand into:

```text
data/cache/clinc150/
```

No CLINC150 rows are committed to this repository.

## Comparison: Closed-Set Routing vs Open-Set Calibration

`routing` is fundamentally distinct from `calibration`:

1. **Routing (`01-routing`) is Closed-Set Classification:**
   The model is instructed that the query **guaranteed belongs to one of the 77 supported banking categories**:
   ```text
   Customer Query
         ↓
   {intent_1, intent_2, ... intent_77}
         ↓
   Choose exactly one
   ```
   *Routing answers: "Which of the 77 doors is the right door?"*

2. **Calibration (`02-calibration`) is Open-Set / Out-Of-Scope Detection:**
   The model is presented with both in-scope banking queries and out-of-scope requests (drawn from CLINC150) mapped to an explicit `other` option:
   ```text
   Incoming Query (In-Scope or OOS)
         ↓
   {intent_1, intent_2, ... intent_77} + "other"
         ↓
   Classify into banking intent OR reject as "other"
   ```
   *Calibration answers: "Do you know when NONE of the 77 doors is the right door?"*

Together, these two tasks verify whether:
- The system accurately routes valid domain requests across a complex 77-class intent topology;
- The system reliably detects out-of-domain requests without hallucinating a banking intent;
- The confidence score drops gracefully on borderline or out-of-scope queries.

## Profiles

`compare-public` and `run_local_matrix.py` expose four cost/coverage profiles. When a profile uses a subset of the dataset, the sampler applies **deterministic class-balanced sampling** (fixed seed=42) to ensure fair representation across all 77 intents:

| Profile | BANKING77 routing | Examples / class | Calibration in-scope | CLINC150 OOS | Intended use |
|---|---:|---:|---:|---:|---|
| `budget` | 77 | 1 per class | 40 | 40 | Fast, cost-efficient sanity run across all classes |
| `quick` | 154 | 2 per class | 100 | 100 | Integration check / cheap comparison |
| `standard` | 770 | 10 per class | 500 | 500 | Default meaningful experiment |
| `full` | 3,080 | ~40 per class (all) | matched to filtered OOS | all filtered OOS | Highest-coverage scientific benchmark |

The BANKING77 routing sampler is strictly class-balanced for all subset profiles (`budget`, `quick`, `standard`).
